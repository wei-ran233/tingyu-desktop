# 插件参数恢复默认与请求合并验收（2026-10-21）

## 已完成行为

插件的统一设置表单增加“恢复默认参数”。仅恢复当前插件通过 manifest.settings 声明的参数；启用状态、其他插件参数、原生 DJ 等独立设置不变。只有宿主窗口可调用 plugin_reset_settings，公共隔离插件 API 仍为 1.4.0，没有暴露任意 reset 方法。

服务将保存与恢复操作放在同一插件串行锁内。恢复成功时清除该插件的参数覆盖文件，返回当前 schema 默认值；后续包版本的新默认值可自然生效。参数确实变化时才复用已提交设置通知，实时更新宿主表单、隔离页面和相关提供器，并取消旧快照请求。删除失败会报告错误，不发成功通知，也不阻塞后续正常写入。

## 实机发现并修复的边界问题

初次实机新增场景暴露了请求堆积：连续 catalog 通知可重复加载，队列繁忙还被误分类为插件故障，导致健康提供器被隔离。早期失败日志保留，不作为验收通过证据。

修复分为以下几层：

1. 页面刷新使用 latest loader，同一时刻最多执行一次加载；期间的请求合并为最后一次输入，过期结果不发布，隐藏或卸载后的回调不更新页面。
2. 运行时队列繁忙使用主进程的独立错误类型，只拒绝该调用，不隔离健康插件；插件自身的异常、非法输出和真正超时仍沿用原隔离规则。

3. 隔离页面的 settings/storage/转发请求共用每插件 16 槽限制，在进入读写串行链之前占槽；超出直接拒绝，不排无界队列。
4. runtime 在 getSettings 文件读取之前占用 16 槽，完成、取消或异常均释放。主题、设置、集合提供器和插件管理共用合并后的目录读取；集合视图另加修订和卸载保护。

最终实机：60 次连续 catalog 事件只触发 1 次目录 IPC；18 个并发请求只有 16 个进入 settings 文件读取；隔离页面的 64 次 storage 突发产生 48 次 busy 拒绝，释放后可正常读写。恢复默认取消旧覆盖值请求，并在同一运行实例中显示默认值。

## 分工与执行记录

设置页局部修改与服务契约测试分别交给独立子 agent，主线负责持久化协议、IPC、整合、故障定位及最终实机验收。对参与实现及首轮审查的四个实际子会话的检查记录在 `subagent-audit.json`：有效模型均为 ccs-opencode/deepseek-v4.1-flash、思考强度 max；调用显式设置 fork_turns=none，并确认子会话有真实工具调用。已检查的启动记录未包含父聊天的历史请求，也未观察到实际 compacted 事件；共享 AGENTS 文本中的 CompHashChanged 字面量不作为压缩发生的证据。

独立审查指出的 RESET DEBUG 残留已清理。后续审查发现的三项边界均已修复并由主线逐项核对：settings/storage 限流覆盖、runtime 在 I/O 前预留槽位、集合目录的合并与修订保护。后续交接出现空任务、返回旧发现或无关额度信息，已停止追加委派；这些返回不计为复核通过，新修复以主线源码核对和上述实机计数验收为准。任务进度、前后快照及审查差异保存在本计划的 `.superpowers/sdd/` 目录，未制造用于审查的提交。
