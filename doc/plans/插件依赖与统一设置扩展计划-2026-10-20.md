# 插件依赖、统一设置与开放扩展计划

> 当前进度入口（2026-10-21）：见[当前计划状态与后续实施清单](当前计划状态与后续实施清单-2026-10-21.md)。第一阶段已有验收；第二阶段已完成 lifecycle/processor/provider/action/event，声明式UI已交付搜索试点，其余业务挂载点和主题资源等仍待实施；第三阶段部分基础能力存在、整体未完成。下文保留各阶段当时的计划与记录，“尚未实现”应结合后续日期阅读。

## 现状审计与目标

审计基线为 2026-10-20 本地工作区。已有 33 个原生功能、90 个渲染注册、17 个原生设置贡献，第三方包支持隔离页面、集合视图、主题、命名空间存储。功能模型与渲染模板分离已经实现，但这不等于任意插件均可增强另一插件。

审计发现：通用 `PluginManifest` 没有依赖与设置声明；内置依赖只在 `common/bundles` 内静态定义；设置主菜单从 `NATIVE_SETTINGS` 生成；主题另设顶级入口；主进程没有第三方通用服务的异步 activate/deactivate；第三方渲染也不能向任意功能注册模型增强。故当前不能宣称“万物皆可扩展”。

目标是：所有业务能力经明确、可版本化的扩展点开放；设置、功能、渲染、主题遵守相同的依赖与生命周期。宿主保留签名、隔离、授权、恢复入口等最小平台能力。依赖不会授予另一个插件的内存、文件、凭据或任意 IPC 权限。

## A 增强 B 的确定规则

1. A 必须声明 B 为必需依赖，并给出支持的版本边界。B 不存在、未启用、不兼容或依赖失败时，A 保留安装和用户启用偏好，但有效状态为 blocked，所有运行贡献停止提供，管理页和设置页说明原因。
2. 注册顺序由依赖图决定：B → A；多个无依赖关系的插件按稳定 ID 排序，不依靠文件名、安装先后、setTimeout 或用户手动排序。
3. 通用异步服务阶段还须 await B.activate 成功，再执行 A.activate；拓扑排序本身不能证明 B 已完成初始化。失败要向依赖链传播，不向无关插件传播。
4. 停用顺序为 A → B；停止接收新请求、取消在途操作、撤销 A 的贡献并等待其 dispose，然后释放 B。卸载/更新/回滚也重新解析整张图，不能仅关闭 B 自己的窗口。
5. B 恢复后只恢复仍被用户启用的 A；不自动安装、下载、启用依赖。依赖不满足的包允许先安装，便于安装顺序无关；有效激活必须失败关闭。
6. 必需依赖循环、自依赖、重复依赖、无效版本范围均不可激活。缺失、关闭、版本冲突、循环应有不同可读原因。
7. “只在 B 已存在时增强、没有 B 仍有其他用途”属于可选集成。另行声明 optionalDependencies 和集成点，不与本次必需依赖混用。

示例约定：

```json
{
  "id": "example.enhancer-a",
  "apiVersion": "1.2.0",
  "dependencies": [
    { "id": "example.feature-b", "minVersion": "1.0.0", "maxVersionExclusive": "2.0.0" }
  ]
}
```

使用明确的最小版本（含）和最大版本（不含）；第一阶段不接受含义不清的任意版本表达式。

## 第一阶段：依赖契约与设置整合（本轮实施）

- 为所有插件统一解析必需依赖图，输出有效可用性、阻塞原因和依赖在前的贡献顺序。页面、主题、集合视图、资源协议与插件请求均检查有效状态。依赖失效时销毁整条受影响链的隔离视图。
- 在签名清单加入依赖与受限设置字段声明，API 升到 1.2，兼容原 1.0/1.1 包；旧包不改变签名载荷。
- 每个已安装插件自动拥有设置入口，至少显示启用状态、版本、权限、依赖与不可用原因；有配置项的插件可声明布尔、数字、短文本、枚举，由宿主统一渲染、校验和按插件命名空间保存。没有额外参数的插件明确显示“无额外参数”。
- 主题选择、动效开关与恢复默认移到“设置 → 常规 → 主题与外观”；移除独立导航入口。保留旧 `/themes` 地址重定向，已有书签不失效。插件管理中的主题应用按钮改为前往设置。
- 官方设置功能关闭时保留宿主设置恢复入口；主题设置和插件默认设置不能依赖它们所管理的插件本身。
- 原有 DJ 等复杂设置继续使用已有模型与统一表单容器，不能为了通用 schema 改写凭据、保存语义或丢失草稿。通用 schema 第一阶段不承载密钥字段。

第一阶段中的“依赖在前”指声明式贡献的解析和开放顺序，不表示已经实现第三方后台服务的异步初始化。当前隔离页面仍按需创建。

## 第二阶段：通用生命周期与跨插件扩展点（生命周期与 processor 试点已实施，其余待迁移）

- 引入 `installed/disabled/blocked/resolving/activating/active/stopping/failed` 状态机及每个插件的串行操作队列，激活超时、AbortSignal、dispose 栈、错误隔离、回滚与崩溃熔断。
- 扩展点由提供方 B 声明 ID、版本、输入/输出 schema、作用域及支持方式。A 只能声明实现/装饰已公开的点，不直接替换 B 内部对象、拦截任意 IPC 或注入未审查代码。
- 功能点支持 provider、processor、action、event；渲染点支持 renderer、slot、toolbar；主题点支持 tokens、assets、layout、motion。功能处理器不能把 UI 或 DOM 混进模型契约。
- 同一功能允许多个渲染器，用户选择与主题临时覆盖分开；多个增强器的冲突采用显式优先级和稳定 ID，支持停用任意增强器并撤销它的影响。
- 签名第三方代码继续在隔离宿主运行，能力授权绑定调用者、目标点与版本；依赖关系不隐含跨插件权限。无法授权的能力不启动。
- 先用“一个原生功能 B + 一个隔离增强包 A + 两个独立渲染”试点，实测 B 缺失/失败、A 超时、切换渲染、更新回滚和逆序撤销，再逐步迁移音乐源、播放队列、歌词、评论、导航、下载、电台等业务。

## 验收矩阵

| 场景 | 必须满足 |
| --- | --- |
| B→A→C，乱序安装/启动 | B、A、C 顺序一致，缺 B 时 A/C 不可用 |
| B 停用/移除/不兼容/更新/回滚 | A/C 资源和请求立即不可用，隔离视图清理；偏好不丢失 |
| 循环/菱形/独立插件/版本边界 | 循环阻塞，菱形只激活一次，独立插件不受影响 |
| 有/无设置声明 | 每个插件都有入口；表单一致；无参数提示明确 |
| 参数验证与重启 | 类型/范围/枚举非法值拒绝；并发修改不丢失；重启保留 |
| 主题与设置入口 | 旧地址能跳转；无顶级主题导航；禁用主题恢复；官方包关闭仍能管理 |
| 跨插件增强试点 | await 初始化、超时、取消、逆序 dispose、版本与权限拒绝均有实际测试 |

## 执行记录

第一阶段已实现，API 为 `1.2.0`：

- `common/plugin/dependencies.ts` 解析必需依赖、版本边界、传递阻塞与稳定拓扑顺序。`PluginService.list()` 返回用户开关与有效可用性两个维度；安装不自动启用依赖。
- `PluginService.getEntry()` 对插件请求和资源读取统一检查有效可用性；页面、主题、集合提供器目录同步排除阻塞贡献。依赖变更时关闭受影响的隔离视图并拒绝在途宿主请求。
- `common/plugin/settings.ts` 校验受限配置值；主进程按插件 ID 保存设置，串行合并修改、临时文件写入后原子替换；卸载删除相应设置。宿主可查看已停用插件的设置，但不可写入不可用插件。
- 每个插件自动出现在插件设置二级菜单。未声明额外参数的插件仍有启用、版本、权限、依赖与状态；原生插件提供其已有专用设置链接。
- 插件可通过 `settings.scoped` 权限声明字段，并用 `window.lxPlugin.settings.get()`、`.set(key, value)`、`.subscribe(callback)` 访问自己的设置，不能传入别的插件 ID。Card Gallery 的 `guideTitle` 是真实样例，宿主修改可推送到隔离页面。
- `/themes` 重定向到 `/setting?name=ThemeSettings`。侧栏不再提供独立主题页，主题选择与动效归入设置。`/preferences` 为官方设置功能停用时的宿主恢复页，支持主题管理和所有插件默认设置。
- 电台包和主题包现在都在签名清单中声明对 `lx.official-suite` 的必需依赖。主题包版本更新为 `1.2.0`，Card Gallery 为 `1.1.0`。

第一阶段验收时的边界为：拓扑顺序仅代表贡献顺序。后续实现见下方第二阶段记录。尚未迁移的 provider/action/event、渲染插槽与主题资源契约仍不能视为完成；不把本项目描述为完全通用的插件生态。

## 第二阶段实施记录（2026-10-20）

API 升级为 `1.3.0`，兼容 1.0/1.1/1.2 包。新增签名字段 `runtime`、`extensionPoints`、`extensions`、`defaultEnabled`，以及 `extensions.process` 权限。旧包缺省字段不进入签名载荷。

已完成的生命周期：

- `PluginLifecycle` 串行解析与激活，只有依赖状态为 active 才调用依赖者的启动；后台模块的异步 activate 必须完成，才会发布 active 状态与贡献。
- 停用、更新、回滚、移除前，立即撤销有效性并取消受影响请求，再逆序等待依赖者与提供方 dispose。单个 dispose 最多等待 1 秒，之后强制销毁隔离环境；激活超时由清单声明，宿主限制为 100–10000ms；处理请求最多 2 秒。
- 运行时初始化失败、崩溃或返回非法输出后进入失败隔离，不自动循环重启。依赖者阻塞，无关插件继续工作；用户重新启用或更新后可重试。失败清理不自动使用旧目录重新激活，避免与安装/回滚事务竞态。
- 更新使用签名作为运行代际标识，代际改变后重新准备依赖链。处理中的旧代际结果、停用后的迟到结果均拒绝；资源和插件请求继续检查有效可用性。
- 运行态可在插件设置中查看；宿主故障诊断可读取有界生命周期事件，不向隔离插件暴露管理 IPC。

已完成的受限功能扩展：

- B 在清单公开 processor 扩展点的 ID、精确版本和有界数据 schema；A 必须声明对 B 的必需依赖、扩展权限、目标点、支持版本和本包处理器名称。
- schema 当前支持字符串、有限数字、布尔和有界嵌套对象，拒绝额外字段和可执行校验器。processor 的输入输出必须一致；所有输入、每一步输出都校验并复制，处理器不共享对象引用。
- 多个 A 按 priority、插件 ID、扩展 ID 稳定排序。依赖顺序管理初始化，priority 只管理同一处理链的处理顺序，两者不混淆。
- 运行时代码在隐藏的 Electron 沙箱中执行，关闭 Node、任意 IPC、外部网络、跨插件资源、弹窗和 WebView。使用独立会话和已有签名资源协议；启动期间的资源读取有专门宿主路径，仍校验依赖、签名与文件摘要。
- 宿主内部使用 AbortSignal；跨 contextBridge 的回调通过 `isCancelled()` / `onCancel(callback)` 提供取消语义，避免把原生 AbortSignal 当可克隆对象传输。

实际试点：B 为 `lx.official-suite` 的 `search.query@1.0.0`，A 为独立签名包 `lx.search-cleaner`。A **默认关闭**，在“设置 → 维护与扩展 → 搜索词整理”启用；它将 `"  成都　   赵雷  "` 整理成 `"成都 赵雷"`。参数 `collapseSpaces` 控制是否合并连续空白。原版搜索与潮汐独立渲染都使用原来的搜索功能模型和同一处理结果；关闭 A 后恢复原输入。处理的是用户已输入的搜索词，不读取歌单、凭据或播放数据。

新代码入口：`src/common/plugin/extensions.ts`、`src/main/modules/plugin/lifecycle.ts`、`runtimeHost.ts`、`renderer/runtimePreload.ts`、`src/renderer/core/pluginExtensions.ts` 与 `plugin-samples/search-cleaner/`。构建必须同时包含 main、renderer、renderer-scripts 和签名插件包。

本阶段还未完成：通用 provider/action/event、renderer/slot/toolbar 注册、动态主题 assets/layout/motion、可选依赖、配置迁移与凭据存储。它们按第二、三阶段继续扩展，不通过任意对象修改或放开 Node 权限来绕过契约。
